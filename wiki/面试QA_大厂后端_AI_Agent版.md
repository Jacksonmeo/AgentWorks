### Q2：用两分钟介绍 AgentWorks

**参考回答【代码可核实】：**

> AgentWorks 是一个面向客服场景的多 Agent 编排运行时。请求进入 `/chat` 后，系统先从 Redis 和 ChromaDB 读取当前会话、历史摘要和用户画像，再用 LLM Few-shot、字符 n-gram 相似度和 Pattern 三路融合识别 19 类意图，同时提取订单号、金额、日期和错误码等实体。

**面试官可能继续追问：**为什么是多 Agent、RAG 到底何时触发、三路融合怎么投票、指标怎么测、失败如何降级。

## 3. AgentWorks 项目深挖

### 3.1 架构与多 Agent

### Q3：为什么要做多 Agent，而不是一个大 Prompt？

**参考回答【代码可核实】：**

> 我采用多 Agent 的核心原因不是“多个名字”，而是客服问题存在不同的输入契约、工具权限和风险边界。Technical 需要错误码、环境和复现信息；Billing 需要订单、金额、渠道并避免未经核验承诺退款；General 负责分诊；Escalation 只生成交接信息。代码里每类 Agent 都有独立的 `AgentProfile`、温度、最大输出长度、工作流和工具白名单。复合问题还能并行处理。  
> 代价是调用次数、延迟和合并冲突都会增加。因此简单问候、单领域问题只走一个 Agent；只有多个领域得分同时达到阈值时才并行。如果业务规模很小、工具权限也相同，我会优先用单 Agent，没必要强行拆分。

### Q4：这是真正的多 Agent，还是多个 system prompt？

**参考回答【代码可核实】：**

> 不只是 system prompt 不同。差异包括四层：结构化角色契约、领域专属输入包、不同工具白名单、主辅路由与结果合并。比如 Technical 能调用错误码解释和诊断计划工具，Billing 能检查账单字段和比较金额，Escalation 是不调用 LLM 的确定性交接节点。  
> 但我也会承认它仍是单进程内的轻量编排，不是跨服务的自治 Agent 集群；“多 Agent”描述的是职责与执行图，不应夸大为分布式系统。

### Q5：系统中到底有几个 Agent？

**参考回答【代码可核实】：**

> 有 3 个业务 Agent：General、Technical、Billing，另有 1 个 Escalation 人工升级节点。简历写“三类 Agent”指三类业务处理角色；如果把交接节点算上，运行时一共有四种 `AgentType`。面试时我会主动说明，避免口径冲突。

### Q6：一次请求的完整链路是什么？

**参考回答【代码可核实】：**

> `/chat` 先读取记忆，构造最近对话；然后做意图识别、紧急度判断和实体提取；Orchestrator 计算领域分数，生成主 Agent、辅助 Agent、路由原因和置信度；业务类意图会在 Agent 执行阶段预取共享知识库，非业务意图跳过 RAG；多 Agent 场景由 Composer 合并；最后把用户消息和回答写回 Redis，并按条件异步更新 ChromaDB 用户画像。Monitor 定时读取累计统计，Evaluator 通过独立接口触发。

### Q7：复合问题如何判断并行？

**参考回答【代码可核实】：**

> 系统为 General、Technical、Billing 分别打分。意图命中专业域时加 0.75，领域关键词按命中数加分，错误码、金额、订单号等实体再补分。最高分是主 Agent；其他非 General Agent 得分至少 0.45，且不低于主 Agent 的 55% 时成为辅助 Agent。比如“登录报 401，同时被重复扣款”会同时提高 Technical 和 Billing 得分。

**主动说明局限：** 这些权重和阈值目前是启发式配置，仓库没有消融实验。更成熟的做法是用标注路由集或线上成本函数调参。

### Q8：并行执行怎样处理失败和冲突？

**参考回答【代码可核实】：**

> `asyncio.gather(..., return_exceptions=True)` 并行收集结果，只把正常的 `AgentResponse` 交给 Composer。Composer 以主 Agent 为主，要求去重、保留必要步骤、遇到冲突明确核验；如果 Composer 的模型调用失败，就按主结果加“补充说明”做确定性拼接，避免所有内容丢失。专业 Agent 失败时还会降级到 General。  
> 当前不足是 Agent 级 LLM 调用没有外层超时，只有工具管理器有 `asyncio.wait_for` 超时；面试时不能说所有 Agent 都已经具备超时兜底。

### Q9：人工升级是真的创建工单吗？

**参考回答【代码可核实】：**

> 不是。当前 Escalation 节点生成标准化交接摘要并设置 `escalated=true`，代码注释也明确生产环境可再接工单系统、人工队列或 Webhook。它能证明升级决策和交接格式，但不能声称已经创建真实工单。

### Q10：为什么 Escalation 不调用 LLM？

**参考回答【代码可核实】：**

> 升级场景更看重确定性和安全边界。节点直接基于意图、紧急度和实体生成交接信息，避免在高风险投诉、资金或安全场景继续编答案，同时减少一次模型调用。

### Q11：动态路由如何利用成功率和延迟？

**参考回答【代码可核实】：**

> 同类 Agent 的基础评分是 `0.7 × 成功率 + 0.3 × 延迟分`，延迟分是 `1 / (1 + avg_ms / 1000)`；Monitor 再根据低成功率和高延迟写入最高 0.9 的惩罚项。`_best_agent()` 在同类型实例中选择最终评分最高的实例。

**必须补充的边界：**默认池中每类只有一个实例，所以机制存在，但默认配置下不能真正“绕开同类坏实例”。要证明动态路由有效，需要增加同类实例并做故障注入实验。

### Q12：这套编排与 LangGraph 有什么关系？

**参考回答：**

> AgentWorks 当前仓库使用自定义 Python Orchestrator 和 `asyncio`，没有使用 LangGraph。LangGraph 出现在我的 GIS Agent 实习经历中，两者不能混讲。AgentWorks 适合规则明确、节点较少的流程；如果要加入持久化 checkpoint、复杂条件边、多阶段人工审批或可恢复执行，我会考虑 LangGraph。

### 3.2 意图识别与路由

### Q13：19 类意图具体有哪些？

**参考回答【代码可核实】：**

> `query`、`complaint`、`request`、`greeting`、`escalation`、`technical`、`billing`、`account`、`feedback`、`order_status`、`logistics`、`refund`、`invoice`、`payment_issue`、`account_security`、`technical_login`、`technical_crash`、`human_handoff`、`other`。其中部分是通用大类，部分是细粒度业务类；细粒度意图会映射到 query、billing、account、technical、escalation 等意图组。

### Q14：三路融合具体怎么做？

**参考回答【代码可核实】：**

> LLM 使用每类一个 Few-shot 示例并结合最近三轮上下文；相似度分支把消息和模板转成向量，取最高余弦相似度；Pattern 使用高精度关键词。正常情况下三路权重是 0.7、0.2、0.1，对各自候选意图的置信度加权，最高分低于 0.5 则返回 `other`。此外，如果融合结果是宽泛大类，而 Pattern 高置信命中细粒度意图，代码会做细粒度修正。

### Q15：Embedding 用的是什么模型？

**参考回答【代码可核实，容易答错】：**

> 意图识别分支会先检查客户端是否提供 embeddings 接口；如果没有，就使用本地 256 维字符 n-gram 哈希向量。标准 Anthropic SDK 当前通常没有该 embeddings 资源，因此不能把这一支笼统说成高质量语义 Embedding 模型。  
> ChromaDB 知识库和长期记忆的向量化是另一条链路，当前依赖 ChromaDB 默认 embedding。两者必须区分。

### Q16：为什么权重是 0.7 / 0.2 / 0.1？

**诚实回答【必须补证】：**

> 目前这是基于能力定位的启发式初值：LLM 处理复杂语义，相似度提供模板邻近证据，规则提供确定性兜底。仓库里没有能证明这是最优权重的消融报告，所以我不会说“实验得出最优”。如果继续完善，我会固定测试集，网格搜索权重和阈值，并按 Macro-F1、关键类召回率、成本和延迟共同选择。

### Q17：LLM 不可用时怎么办？

**参考回答【代码可核实】：**

> LLM 分支异常会返回失败标记，融合逻辑优先采用相似度分支，再采用 Pattern；两者都没有结果才返回 `other`。查询改写或重排失败时也会分别回退到原查询和原始顺序。

**局限：**LLM 失败分支当前只要相似度大于 0 就可能接受候选，没有复用总阈值，可能导致低质量分类；这是可改进点。

### Q18：低置信度如何处理？

**参考回答【代码可核实】：**

> 融合分数低于 0.5 会得到 `other`。如果消息长度大于两个字符且仍低置信，Orchestrator 不会强行路由，而是询问用户属于订单物流、退款账单、账户资料还是技术故障。很短的问候不会被这条规则误拦截。

### Q19：意图识别为什么需要上下文？

**参考回答【代码可核实】：**

> “多久到账”“还是不行”这种消息单独看不完整。系统把最近三轮上下文放进 LLM 识别 Prompt，并把消息加历史内容共同计算缓存键，避免相同短句在不同上下文中命中同一个错误缓存。Pattern 和本地相似度仍只看当前消息，这是性能与语义之间的折中。

### Q20：实体提取怎么做？

**参考回答【代码可核实】：**

> 当前用正则提取订单号、日期、金额和 4xx/5xx 错误码，避免为少量高价值字段额外调用 LLM。优点是快、可解释；缺点是产品实体为空、复杂时间表达和金额上下文处理较弱，也没有实体评测。生产方案可使用规则加 NER/结构化输出，并对字段单独计算 Precision、Recall、F1。

### Q21：缓存是 LRU 吗？

**参考回答【代码可核实，建议主动纠正】：**

> 代码注释写了 LRU，但实现实际上是普通字典达到 1000 条后批量删除前 500 个，更接近按插入顺序批量淘汰，不是真正的访问型 LRU。准确介绍时我会称它为“有界进程内缓存”；要做严格 LRU 可用 `OrderedDict` 或专门缓存库。

### Q22：如何处理类别不均衡？为什么看 Macro-F1？

**参考回答：**

> Accuracy 容易被高频大类掩盖，Macro-F1 是先对每个意图计算 F1 再等权平均，更能暴露退款、转人工、安全等低频类是否失效。实际评测还应看每类混淆矩阵，尤其关注高风险类的 Recall；当前代码计算了 per-class Precision、Recall、F1，但仓库没有保存 500 条数据集或混淆矩阵报告。

### 3.3 RAG 与工具治理

### Q23：RAG 的完整链路是什么？

**参考回答【代码可核实】：**

> 文档先按约 500 字、尽量按句号边界切片并写入 ChromaDB。检索时 LLM 生成三个改写查询，同时保留原查询，所以最多是四路并行召回；合并结果后去重，再由 LLM 返回相关性顺序，截取 Top-K。工具管理器还提供 300 秒缓存、默认 30 秒超时、三态熔断和 fallback。

### Q24：查询改写、召回、重排各解决什么问题？

**参考回答：**

> 查询改写解决用户表达和知识库措辞不一致；多路召回提高候选覆盖率；重排解决向量距离不完全等价于任务相关性的问题。它们分别主要影响召回、候选覆盖和排序质量，但也会增加模型调用、延迟与成本，所以不能对所有问题无条件开启。

### Q25：你说“3 路并行召回”，到底是 3 路还是 4 路？

**参考回答【代码可核实】：**

> `rewrite_query(query, n=3)` 会返回原查询加三个改写结果，去重后最多四个查询。因此简历更准确的表述是“生成 3 个改写子查询，并保留原查询并行召回”，而不是简单说只有三路。

### Q26：意图门控 RAG 是如何生效的？

**参考回答【代码可核实】：**

> 意图识别结果会随请求传给目标 Agent。Agent 对查询、请求、投诉、技术、账单、订单、物流、退款等业务意图预取一次共享知识库；问候和反馈直接跳过 RAG。预取成功后，检索结果被注入当前消息，并关闭后续知识库工具规划，避免同一轮重复检索。

### Q27：如何去重？现在的实现有什么问题？

**参考回答【代码可核实】：**

> 当前对整个结果对象的字符串做 MD5。问题是对象里包含 `score`，同一文档在不同查询下得分变化时，序列化内容也会变化，可能没有真正去重。更稳妥的键应是文档 ID，或 `title + chunk_index + content_hash`；同时保留多路中的最高分和命中来源。

### Q28：重排失败怎么办？如何防止非法索引？

**参考回答【代码可核实】：**

> 重排要求 LLM 返回索引数组，只接受 `0 <= i < len(items)` 的索引；解析或调用失败就返回原始顺序的 Top-K。当前还应补充索引去重、缺失候选回填和结构化 Schema 校验，否则模型可能重复索引或漏掉结果。

### Q29：ChromaDB 的 score 是余弦相似度吗？

**参考回答【代码可核实，当前有风险】：**

> 当前代码用 `1 - distance` 生成 score，并在注释里称为相似度，但 collection 创建时没有显式设置 `hnsw:space=cosine`。因此不能严格保证这个数就是余弦相似度；它更多是展示值。应显式指定距离度量，并根据 ChromaDB 返回语义正确转换，评测也不要直接把该展示值当概率。

### Q30：文档切片为什么是 500 字？有 overlap 吗？

**参考回答【代码可核实】：**

> 500 字是简单经验值，代码尽量按句号或换行边界切分，没有 overlap，也没有按标题层级和 Token 计算。好处是实现简单；缺点是跨块信息可能丢失。要证明 500 最合适，需要在真实问答集上对 chunk size、overlap、Top-K 做检索评测，而不是凭经验下结论。

### Q31：缓存、超时、熔断是怎样实现的？

**参考回答【代码可核实】：**

> 工具调用顺序是缓存检查、熔断检查、Schema 参数校验、`asyncio.wait_for` 执行、可选重排和缓存写入。默认工具超时 30 秒；连续失败 5 次打开熔断，60 秒后进入 half-open，成功则关闭，失败则重新打开。知识库工具配置了 300 秒进程内 TTL 缓存。

### Q32：这套熔断器能直接用于生产吗？

**参考回答：**

> 还不能直接当成分布式生产熔断。状态保存在单进程内，没有锁和跨实例共享；half-open 状态也可能同时放行多个并发探测。多副本环境应使用成熟库或共享状态，并限制 half-open 探测并发，同时区分超时、限流、参数错误等失败类型。

### Q33：fallback 返回 success=true 合理吗？

**参考回答【代码可核实】：**

> 当前 fallback 成功生成降级内容时，`ToolResult.success` 为 true，同时保留 `error`。这样上游还能继续回答，但“工具业务成功”和“系统成功降级”混在一个字段里。更严谨的结果应区分 `status=success/degraded/failed` 或增加 `fallback_used`，监控也分别统计，否则成功率可能被美化。

### Q34：如何计算“检索召回率 91.2%”？

**诚实回答【必须补证】：**

> 当前仓库没有检索 gold set、相关文档标注或 Recall@K 计算代码，无法证明 91.2%。合理口径应是：每个问题预先标注一个或多个相关文档 / chunk，统计 Top-K 是否覆盖这些相关项，计算 `Recall@K = 检索到的相关项数 / 全部相关项数`，并固定知识库版本、K、embedding 和 rerank 配置。拿不出这些材料时，应删掉 91.2%。

### Q35：如何计算“回答准确率 88.7%”？

**诚实回答【必须补证】：**

> 当前 Evaluator 有 LLM-as-Judge 的 `accuracy` 维度，但没有 88.7% 的原始报告，也没有独立人工标准答案集。必须先说明这到底是人工判对率、Judge 平均分，还是事实一致性指标；三者不能混用。如果只是 Judge 的平均 accuracy score，应写“LLM-as-Judge 准确性维度均分 0.887”，而不是笼统写回答准确率。

### Q36：RAG 最大的性能瓶颈是什么？

**参考回答：**

> 最坏路径包括一次意图 LLM、一次查询改写、最多四次并行向量检索、一次重排、Agent 一到三轮 LLM，多 Agent 时还要并行多个 Agent 并调用 Composer。向量检索本身未必最慢，主要延迟和成本来自多次 LLM。优化方向是严格门控、缓存、候选数上限、按问题复杂度跳过改写或重排、不同阶段使用更轻模型，并记录分阶段 P50/P95；当前仓库没有 P95 压测报告。

### 3.4 分层记忆与动态 Skills

### Q37：为什么 Redis 和 ChromaDB 都要用？

**参考回答【代码可核实】：**

> Redis 适合当前会话的有序消息、低延迟读写和 TTL；ChromaDB 适合对历史摘要做语义检索，并持久化用户画像。把所有历史都塞进 Prompt 会造成 Token 膨胀，把所有内容都放向量库又不利于精确保留最近顺序，因此做了分层。

### Q38：记忆压缩何时触发？压缩后保留什么？

**参考回答【代码可核实】：**

> 工作记忆达到 15 条时触发，旧消息由 LLM 总结，摘要写 Redis，同时写入 ChromaDB `episodic`；工作记忆只保留最近 5 条。Redis 消息和摘要 TTL 都是 24 小时，情景记忆持久化。已有摘要和新摘要会再次合并，并截断到 800 字。

### Q39：压缩失败怎么办？

**参考回答【代码可核实】：**

> 摘要调用失败时生成“包含多少条消息”的占位摘要，并继续保存原对话的前 500 字到情景记忆 metadata。这样流程不会中断，但语义信息会明显丢失。更好的方案是保留待重试队列、使用确定性抽取兜底，并评测压缩前后关键事实保留率。

### Q40：历史记忆如何避免串用户？

**参考回答【代码可核实】：**

> Redis key 包含 `user_id` 和 `conv_id`。情景检索先按 `user_id + conv_id` 过滤，不足 Top-K 时再退到同一 `user_id` 的跨会话记录；用户画像用 `user_profile:{user_id}` 作为稳定 ID。  
> 但这只是逻辑隔离，不等于完整的隐私方案；仓库还没有租户 ID、鉴权、加密、数据删除 API、敏感信息脱敏和保留策略。

### Q41：异步更新用户画像有什么风险？

**参考回答【代码可核实】：**

> `/chat` 用 `asyncio.create_task` 后台更新画像，能减少响应阻塞，但任务没有持久队列、重试和生命周期跟踪；进程退出时可能丢失，并发请求也可能发生 delete-add 竞争。生产环境应改为消息队列或任务系统，增加版本号、幂等和失败重试。

### Q42：Skills 和 RAG 有什么区别？

**参考回答【代码可核实】：**

> RAG 提供“事实是什么”，例如退款政策；Skills 约束“应该怎么处理”，例如需要收集哪些字段、何时升级、不能承诺什么。事实文档适合检索，稳定的流程和安全边界适合按 Agent 注入。两者混在知识库里会让行为规则容易漏召回。

### Q43：动态 Skills 如何匹配和热更新？

**参考回答【代码可核实】：**

> SkillManager 扫描 Markdown、JSON、TXT，优先识别 `SKILL.md`。Markdown 顶部用轻量 front matter 指定名称、关键词、Agent 和启用状态。运行时先匹配 Agent 类型，再匹配关键词，最后把命中内容拼到 system prompt，总长度上限 5000 字。`POST /skills/reload` 会重新扫描，不需要重启服务。

### Q44：热更新有什么安全风险？

**参考回答：**

> 当前接口没有展示鉴权、审批、签名和版本回滚；如果 Skill 目录或 reload 接口被滥用，相当于修改系统行为。生产环境应限制写权限，接入认证和变更审核，保存版本与哈希，灰度验证后再切换；同时明确 system prompt 的优先级并做注入测试。

### Q45：如何控制 Prompt 过长？

**参考回答【代码可核实】：**

> 记忆侧只取最近消息、最多五条情景记忆，并做摘要；Skills 侧有 5000 字总上限和单块截断；Agent 角色契约是结构化固定内容。当前不足是没有统一 Token 预算器，各模块按字符独立截断，仍可能叠加超预算。

### 3.5 监控与评测

### Q46：Monitor 采集哪些指标？

**参考回答【代码可核实】：**

> Agent 侧采集累计调用数、成功率、平均延迟、路由评分和监控惩罚；工具侧采集调用数、成功率、平均延迟、连续失败和熔断状态。Monitor 默认每 10 秒读取一次，做阈值告警和滑动窗口 Z-score 异常检测，并可暴露 Prometheus 指标和发送 Webhook。

### Q47：Monitor 真正形成闭环了吗？

**参考回答【代码可核实但效果未验证】：**

> 代码闭环是存在的：Monitor 根据成功率低于 90% 和平均延迟超过 3000ms 计算惩罚，写回 Agent 统计；路由评分再乘以 `1 - penalty`。但默认每类只有一个实例，所以只能改变评分展示，不能体现同类切流效果。需要多实例加故障注入才能验证闭环价值。

### Q48：当前监控实现还有哪些问题？

**参考回答【代码可核实】：**

> 指标是进程内累计值，多副本不会自动聚合；告警列表缺少完整去重和自动恢复；`requests_total` 被注册但没有看到递增；Histogram 周期性观察的是累计平均延迟，不是每次请求样本；trace 也只保存在内存 deque。它更适合作为演示型观测骨架，生产上应在请求边界埋点并接统一指标和 trace 后端。

### Q49：端到端评测怎么做？

**参考回答【代码可核实】：**

> 意图评测把预测与 gold label 对比，计算 Accuracy、Macro-F1 和各类 Precision、Recall、F1。对话评测会真实调用 Orchestrator 生成回复，再由 LLM-as-Judge 从相关性、准确性、完整性和帮助性四维评分，四项均值达到 0.75 判定通过。当前结果与上一次基线相对下降超过 5% 时记为 regression。

### Q50：LLM-as-Judge 有哪些偏差？

**参考回答：**

> 可能有自我偏好、位置偏差、长度偏好、Prompt 敏感性和评分漂移。当前实现只调用一次 Judge，并且 Judge 失败时回退为四项 0.5，这会污染均值。改进方式包括人工校准集、不同模型作 Judge、成对比较、交换答案顺序、多次采样、固定 rubric，以及把 Judge 失败单独排除并报警。

### Q51：为什么不能只看 LLM-as-Judge？

**参考回答：**

> 客观任务要优先用确定性指标，例如意图 gold label、工具调用正确性、引用命中、字段完整性和退款承诺违规率。Judge 更适合评估表达相关性和帮助性。最终应组合离线自动指标、人工抽检、线上业务指标与安全指标。

### Q52：内置评测集有多少条？

**参考回答【代码可核实】：**

> 当前仓库只有 11 条内置意图用例和 5 组对话场景，其中一组是三轮对话。它们用于 smoke test，不足以支撑 500 条评测或稳定的泛化结论。仓库没有找到约 500 条数据集文件。

### Q53：91.3% 和 Macro-F1 0.89 如何回答？

**两种口径，只能按真实情况选一种：**

1. **若确有外部证据：**“评测集共 `[真实数量]` 条，由 `[真实标注方式]` 生成并复核；固定模型 `[名称/版本]`、Prompt `[版本]`、阈值 `[值]`，在 `[日期/commit]` 运行，正确 `[数量]` 条得到 91.3%；19 类分别计算 F1 再平均得到 0.89。弱类是 `[真实类别]`，主要混淆为 `[真实混淆]`。”同时展示数据和报告。
2. **若没有证据：**“这两个数字目前不能从仓库复现，是简历中的待补证效果指标。我不应该把它作为已验证结论；当前只能确认评测代码和 11 条 smoke case 存在。”随后说明会补数据或修改简历。

**禁止回答：**直接复述“约 500 条人工标注”但拿不出文件、标注规范、预测输出和混淆矩阵。

### 3.6 后端工程、测试与部署

### Q54：为什么选择 FastAPI？

**参考回答【代码可核实】：**

> 系统 I/O 密集，包含模型、Redis、ChromaDB 和 Webhook 调用；FastAPI 的 async 接口、Pydantic 数据模型和自动 OpenAPI 文档适合快速构建这类服务。同步 ChromaDB 操作用 `asyncio.to_thread` 避免直接阻塞事件循环。

### Q55：`asyncio.to_thread` 能解决所有阻塞问题吗？

**参考回答：**

> 不能。它只是把同步 I/O 移出事件循环，仍受线程池容量、上下文切换和底层客户端线程安全约束。高并发下应限制并发、复用连接、监控线程池排队，优先使用原生异步客户端；CPU 密集任务则不适合依赖线程绕过 GIL。

### Q56：Tool Calling 如何防止模型乱调工具？

**参考回答【代码可核实】：**

> 每个 Agent 只看到共享 RAG 加自己的领域工具；执行前根据 JSON Schema 检查必填字段、类型和未知字段；最多允许三轮工具调用，并把结果以 `tool_result` 回传模型。工具实现本身是确定性的，也明确不伪造订单查询和退款操作。

**局限：**当前 Schema 校验只覆盖少量基础类型，没有 enum、范围、字符串长度和深层对象校验；工具结果也应做输出 Schema 校验。

### Q57：请求追踪如何实现？

**参考回答【代码可核实】：**

> 每个请求生成短 UUID，请求完成后记录意图、主辅 Agent、工具名、输入、耗时、缓存、重排、错误和升级状态，并提供按 request_id 和最近记录查询的接口。当前只用长度 200 的内存 deque，重启丢失且多副本不共享；生产可接 OpenTelemetry 和持久 trace 后端。

### Q58：如何部署？

**参考回答【代码可核实】：**

> Docker Compose 编排 AgentWorks、Redis、ChromaDB、Prometheus 和 Nginx，配置健康检查、数据卷和服务依赖。Nginx 做入口代理，Prometheus 抓取 `/metrics`。需要注意仓库默认 Redis 密码只适合本地演示，生产应使用 secret 管理、网络隔离、TLS、鉴权和镜像版本固定。

### Q59：当前测试覆盖到什么程度？

**参考回答【代码可核实】：**

> 仓库有 9 个单元测试，主要覆盖 Agent 角色契约、工具隔离、人工升级节点、Composer fallback、共享 RAG 工具、工具参数校验和一次 Tool Calling 往返。它没有覆盖意图融合、RAG 门控、记忆压缩、熔断状态机、并行路由、Monitor 反馈和 API 集成。  
> 本次检查中 Python 编译通过，但本机缺少 `anthropic` 依赖，`pytest` 在收集阶段失败，所以我不能说当前环境测试已全部通过。

### Q60：如果让你补测试，优先补什么？

**参考回答：**

> 第一优先是简历核心主张：用确定性 fake client 测三路融合与低置信澄清；验证复合请求确实产生主辅路由；验证 `/chat` 是否按门控暴露或预取 RAG；对熔断做 CLOSED—OPEN—HALF_OPEN 状态测试；用 fake Redis/Chroma 测 15 条压缩和用户隔离。第二优先才是异常、并发和性能测试。

### Q61：多副本部署会有哪些问题？

**参考回答：**

> Redis 和 ChromaDB 是共享存储，但意图缓存、工具缓存、熔断状态、Agent 统计、Monitor 告警和 trace 都在进程内。多个副本会得到不同缓存与路由判断，重启也会丢状态。生产化需要外部缓存、统一指标与 trace、共享或成熟的熔断策略，并考虑画像更新的幂等和并发控制。

### Q62：你会怎样降低成本和延迟？

**参考回答：**

> 先做分阶段埋点，找出意图、改写、召回、重排、Agent 和 Composer 的耗时与 Token；然后按场景减少调用：确定性问候走规则，低风险单领域用轻模型，简单检索跳过改写或重排，严格门控 RAG，复合问题才多 Agent，结果做语义缓存，并设置请求级总预算和超时。没有实测前不承诺具体降幅。

### Q65：Cesium 飞行路线规划是怎么做的？

**参考回答【源码可核实】：**

> 这部分更准确地说是“固定航线三维漫游与交互控制”，不是自动航线规划或最短路径算法。我基于 Vue3、TypeScript、Cesium 和 Mars3D，把 45 个 `[经度, 纬度, 高程]` 航点传给 `mars3d.graphic.FixedRoute`，配置飞行模型、速度、开始时间、相机和轨迹样式，由 FixedRoute 根据航点和时间驱动飞机模型沿路线运动。

### Q67：“15 分钟生活圈”中的时圈是怎么计算的？

**参考回答【源码可核实】：**

> 主算法是基于 PostGIS 路网和 pgRouting 的可达范围计算，不是直接对起点做圆形 Buffer。接口接收 WGS84 经纬度和最大时间成本 `maxCost`，先校验经纬度范围及时间是否大于 0；再根据出行速度计算理论最大距离。当前配置中步行是 4 km/h、骑行是 12 km/h，900 秒对应的理论最大距离分别是 1 km 和 3 km。  
> 系统先在理论距离形成的搜索范围内查找最近道路，使用 geography 计算起点到道路的米制距离，并取最近道路的 `source` 作为 pgRouting 起点。随后把固定速度换算成米每秒，再乘 `maxCost` 得到可移动距离；调用 `pgr_drivingDistance`，以道路表的 `road_length` 为 cost，找出累计成本不超过该距离的路网节点。  
> 得到可达路段后，查询收集路段的起点和终点，用 `ST_Collect` 聚合，再生成包络范围并通过 `ST_AsGeoJSON` 返回。步行场景如果路网没有结果，或者小于 5 分钟且起点没有落在结果面内，会退化为以理论最大距离生成的 geography 圆形 Buffer。

**算法链路：**

```text
经纬度 + maxCost 秒
  -> 参数校验
  -> 速度 × 时间，换算理论最大距离
  -> 在搜索范围内查找最近道路，取其 source 节点
  -> pgr_drivingDistance 按 road_length 做无向可达性扩展
  -> 取可达道路的 StartPoint / EndPoint
  -> ST_Collect + Hull
  -> ST_AsGeoJSON
  -> Polygon / GeometryCollection / MultiPolygon 解析
  -> 返回 GeoJSON polygon
```

**面试官追问：它是真正按时间计算的吗？**

> 当前是“先用固定速度把时间换算为距离，再按道路长度做路径成本”，属于时间约束的近似实现。它没有直接为每条边配置 `cost_time`，也没有考虑坡度、路况、红绿灯、道路等级或动态速度。正确性还依赖 `road_length` 的单位确实是米；这个字段定义和数据加工过程尚未提供，面试前需要确认。

**面试官追问：步行和骑行路网有何不同？**

> 当前两者使用同一张道路表和同一套 SQL，主要差异是速度配置。没有看到步行道、非机动车道、禁行规则、道路类型或坡度的模式化过滤。因此可以说实现了步行/骑行的不同速度时圈，不能说已经建立了两套严格的交通网络模型。

**面试官追问：为什么不是普通圆形缓冲区？**

> 圆形 Buffer 只表达直线距离，不能反映道路连通性；主流程使用 `pgr_drivingDistance` 按路网累计成本扩展。圆形 Buffer 仅是步行无结果或极短时间异常时的可解释降级，降级结果不应和真实路网等时圈混为一谈。

**必须主动说明的实现边界：**

- `pgr_drivingDistance(..., false)` 按无向图计算，没有建模单行、禁行或反向成本。
- 最近节点逻辑实际取“最近道路记录的 `source`”，不是在独立顶点表中比较 source/target 后精确吸附到最近节点。
- SQL 使用 `ST_ConcaveHull(ST_Collect(...), 1)`；PostGIS 官方语义中参数 1 会得到凸包，因此当前范围可能跨越实际不可达的凹陷区域。若需要贴合路网，应验证更小参数、alpha shape 或基于可达边缓冲聚合的方法。
- 步行有圆形 fallback 和起点包含检查；骑行无结果时直接返回空，两个接口的降级语义目前不一致。
- 路网结果质量、拓扑清洗方法、`road_length` 单位、空间索引和真实精度评测仍没有源码或报告证明。

参考：[pgRouting `pgr_drivingDistance` 官方说明](https://docs.pgrouting.org/3.5/en/pgr_drivingDistance.html)、[PostGIS `ST_ConcaveHull` 官方说明](https://postgis.net/docs/ST_ConcaveHull.html)。

### Q69：PostGIS 用了哪些函数和索引？

**参考回答【生活圈源码可核实】：**

> 在生活圈服务中，`ST_SetSRID` 和 `ST_MakePoint` 构造 EPSG:4326 起点；`ST_Buffer` 构造搜索范围与圆形 fallback；`ST_Distance` 在 geography 上计算米制距离；`ST_Intersects` 过滤搜索范围内的道路；`ST_Transform` 在 4326 与 3857 间转换；`pgr_drivingDistance` 做路网可达扩展；`ST_StartPoint`、`ST_EndPoint`、`ST_Collect` 和 `ST_ConcaveHull` 生成范围面；`ST_AsGeoJSON` 输出 GeoJSON；`ST_GeomFromGeoJSON` 与 `ST_Contains` 检查起点是否在结果面中。最近道路排序还使用了 PostGIS KNN `<->` 运算符。

**索引问题必须诚实回答：**

> Service 查询写法具备利用空间索引的可能，但当前提供的 Context 只定义了 `geometry(LineString,4326)`，没有迁移文件、建表 SQL或 `CREATE INDEX ... USING GIST` 证据。因此我不能声称已经建立 GiST 索引，也没有 `EXPLAIN ANALYZE` 证明执行计划。面试前应补道路表 DDL、拓扑生成脚本、索引定义和一份典型查询执行计划。

**可改进点：**用于半径过滤时可评估以 `ST_DWithin` 替换“先 Buffer 再 ST_Intersects”的方式；PostGIS 官方建议距离过滤优先使用支持空间索引的 `ST_DWithin`。参考：[PostGIS 的 ST_DWithin 建议](https://postgis.net/documentation/tips/st-dwithin/)。

### Q70：为什么经纬度距离不能直接算？

**参考回答【源码可核实】：**

> EPSG:4326 的 geometry 坐标单位是角度，不能直接把结果当作米。生活圈代码在查找最近道路和构造圆形 fallback 时把点或道路转成 geography，因此 `ST_Distance` 和 `ST_Buffer` 使用米；在路网搜索范围 SQL 中则先把 4326 转到 3857，以米为单位 Buffer，再转回 4326 与道路相交。  
> 这避免了最直接的“度当米”错误，但 3857 不是严格等距投影，范围扩大时会产生距离变形；更严谨的方案是使用当地合适的投影坐标系，或统一采用 geography / `ST_DWithin`。PostGIS 官方文档确认 geography 距离以米返回。

参考：[PostGIS `ST_Distance` 官方说明](https://postgis.net/docs/ST_Distance.html)、[PostGIS `ST_Buffer` 官方说明](https://postgis.net/docs/ST_Buffer.html)。

### Q71：GIS Agent 的 LangGraph 图怎么设计？

**参考回答【当前 GeoAgent 后端源码可核实】：**

> 如果问题指 `poiRecSys-main/backend` 中的 GeoAgent，图由两个业务节点组成：`call_model` 负责调用模型、生成终态文本或 Tool Call，`execute_tools` 负责执行工具并把结构化结果作为 `tool` 消息回填。边是 `START -> call_model`；有 Tool Call 时进入 `execute_tools`，执行后回到 `call_model`；没有 Tool Call 时进入 `END`。  
> `AgentState` 保存完整消息流、已执行工具结果 `executions`、已见调用签名 `seen_calls`、模型调用步数 `step` 和最终回复 `reply`。数据库 Session 与原始问题不写入全局状态，而是通过 LangGraph `RunnableConfig.configurable` 按请求注入。同步接口用 `graph.invoke`，SSE 用 `graph.stream(stream_mode="values")`，两者复用同一张图。

**必须说明的边界：** 当前没有 checkpointer、持久化恢复、人工审批节点或跨服务任务队列；默认最多进行 3 次真实模型调用。Provider 即使一次返回多个 Tool Call，路由规范化阶段目前只保留第一个，所以不能说已经支持同轮并行多工具。如果要把这段实现归入实习经历，还必须本人说明仓库归属和个人贡献。

### Q73：如何防止 GIS Agent 重复调用工具？

**参考回答【当前 GeoAgent 后端源码可核实】：**

## 5. 综合技能高概率追问

### Q78：asyncio 的并发与多线程有什么区别？

**参考回答：**

> asyncio 是单线程事件循环上的协作式并发，协程在 `await` I/O 时让出执行权，适合模型、数据库和 HTTP 等 I/O 密集任务；线程由操作系统调度，可运行同步阻塞库，但有切换和线程安全成本。AgentWorks 对原生异步 Redis 直接 await，对同步 ChromaDB 使用 `to_thread`。

### Q79：FastAPI 的 lifespan 为什么适合初始化这些组件？

**参考回答【代码可核实】：**

> 模型客户端、Redis、ChromaDB、ToolManager、Monitor 和 Evaluator 都属于进程级资源。lifespan 可以在服务接流量前统一初始化，在关闭时停止 Monitor 并关闭 Redis，避免每个请求重复创建连接。当前初始化失败会导致服务无法启动，这对关键依赖合理，但也可按业务做可选依赖降级。

### Q80：Redis 为什么用 List？

**参考回答【代码可核实】：**

> 当前会话天然是有序消息流。代码用 `LPUSH` 让最新消息在前，通过 `LRANGE` 取固定窗口，读出后反转恢复时间顺序，并设置 TTL。若需要按消息 ID 消费、消费组或高可靠事件流，Redis Stream 更合适；这里只是工作记忆窗口。

### Q81：你在 AgentWorks 哪里用了 SQLAlchemy？

**诚实回答：**

> AgentWorks 客服仓库没有 SQLAlchemy 依赖或实现，不能把两个项目混讲；但当前 `poiRecSys-main/backend` 可以作为独立证据。GeoAgent 使用 SQLAlchemy 2.x 的 `DeclarativeBase`、`Mapped/mapped_column` 和同步 `Session`，通过 FastAPI `Depends(get_db)` 为每个请求创建并在 `finally` 中关闭 Session；POI、签到、Session 和离线推荐结果映射为 ORM 模型，普通查询使用 `select`，空间表达式通过 GeoAlchemy2 和 `func.ST_*` 构造。  
> 准确边界是：当前不是 AsyncSession；在线接口基本是只读查询，无法用它证明复杂写事务治理；迁移是手写 SQL，不是 Alembic。README 写“SQL 只存在于 Repository 层”也不完全准确，`poi_service.py`、`session_service.py` 和 `recommend_service.py` 仍直接构造 SQLAlchemy 查询；更稳妥的表述是“PostGIS 查询主要集中在 Repository，部分普通查询仍在 Service”。

### Q82：你在哪里用了 SSE？

**诚实回答：**

> AgentWorks 客服仓库没有 SSE 接口；当前 `poiRecSys-main/backend` 则提供 `POST /api/agent/chat/stream`。接口返回 `StreamingResponse(media_type="text/event-stream")`，按 `tool_call -> tool_result -> text -> done` 发送事件，工具参数校验失败时用 `error` 事件表达。LangGraph 执行器通过比较相邻状态快照提取新增 Tool Call 和结果，因此工具阶段确实随执行过程输出。

**必须主动纠正：**回复正文不是模型 Token 级实时流。后端先拿到完整回复，再按每 6 个字符切成 `text` 事件；当前也没有 heartbeat、event id、断线恢复、背压控制或代理缓冲配置，生成器只显式捕获 `ValueError`。所以可以说“SSE 同步 Agent 工具执行状态”，不应说“完整实现了生产级 LLM Token 流式输出”。

### Q83：Pydantic 在项目中解决什么问题？

**参考回答【代码可核实】：**

> API 层用 Pydantic 定义 Chat、评测、知识库导入和 trace 响应模型，完成基础类型校验和 OpenAPI Schema 生成。Agent 内部的工具 Schema 是另一套手写校验，目前没有复用 Pydantic，后续可统一输入输出契约。

### Q84：PostgreSQL 普通索引与 PostGIS GiST 索引有什么差异？

**参考方向：**

> B-tree 适合标量等值与范围排序；GiST 是通用搜索树框架，PostGIS 用它索引几何对象的包围盒，先快速筛选候选，再做精确空间判断。回答后必须接本人实际 SQL 和执行计划，否则仍停留在概念层。

### Q85：前端为什么用 Cesium 而不是 Mapbox？

**参考方向：**

> Cesium 更偏三维地球、地形、3D Tiles 和相机飞行；Mapbox 更擅长矢量瓦片和二维 / 2.5D 地图样式。具体选择由数据形态和交互需求决定。简历同时写了二者，但应准备各自一个真实功能，不要只背对比。

### Q86：如何设计一个可重试的外部接口调用？

**参考回答：**

> 先区分可重试错误：网络抖动、部分 5xx、429；参数错误和多数 4xx 不重试。使用指数退避加 jitter、最大次数和总超时；非幂等操作需要幂等键；结合熔断、限流、监控和降级。AgentWorks 工具层目前有超时和熔断，但没有通用重试，这是可以继续完善的地方。

### Q87：如何解释 REST API 的幂等性？

**参考回答：**

> 幂等指相同请求执行多次，对服务端最终状态影响与执行一次相同。GET、PUT、DELETE 按语义应幂等，POST 通常不保证；支付、退款或创建工单要用业务幂等键、唯一约束和事务防重复。当前 AgentWorks 没有真实资金写操作，不应声称已解决支付幂等。

## 11. GeoAgent 后端专项审计补充

> 本节只核验 `poiRecSys-main/backend` 当前代码和本机测试结果，不把这些实现自动归入 AgentWorks 客服项目或某段实习。源码能证明“机制存在”，不能单独证明个人贡献、真实上线、生产规模或效果提升。

### Q94：GeoAgent 后端的一次请求怎样走完整链路？

**参考回答【代码可核实】：**

> FastAPI Router 接收请求后，通过 `Depends(get_db)` 注入同步 SQLAlchemy Session。普通 POI、轨迹和空间接口进入 Service，再由 ORM 或 Repository 查询 PostgreSQL/PostGIS；Agent 接口则按请求组装 Tool Registry 和 `AgentService`，由 `AgentRunner` 驱动 LangGraph 的“模型—工具—模型”循环。当前 Registry 注册 `query_poi`、`spatial_density`、`recommend`、`track`、`analyze_site_selection` 五个工具。  
> 工具返回结构化结果后，服务统一组装 `reply`、`tool_calls`、`map_layers` 和 `artifacts`。POI、密度、推荐和轨迹分别映射为点、热力或轨迹图层；选址结果使用独立 Artifact，避免前端从自然语言中解析指标和流向。

**架构审计修正：**README 中“SQL 只存在于 Repository 层”的表述过强。空间查询主要集中在 Repository，但 `poi_service.py`、`session_service.py` 和 `recommend_service.py` 仍直接构造 SQLAlchemy `select`。面试时应讲真实边界，不要为了套分层架构而忽略代码现状。

### Q95：GeoAgent 后端实际用了哪些 PostGIS 能力？

**参考回答【代码可核实】：**

> bbox 查询使用 `ST_MakeEnvelope + ST_Intersects`；附近查询把 4326 Point 转为 geography，再用 `ST_DWithin + ST_Distance` 以米筛选和排序；密度分析用 `ST_SnapToGrid + COUNT + GROUP BY`；选址指标用 `ST_GeomFromGeoJSON + ST_SetSRID + ST_Covers` 判断 Polygon 覆盖；候选区重叠时再用 geography 距离选择最近中心。这里的空间结果由数据库计算，不由 LLM 生成。

**必须说明的边界：**仓库当前三份迁移只覆盖 Session、数据质量检查和推荐结果，没有 `pois` 表建表及 `geom` GiST 索引 DDL。ORM 明确设置 `spatial_index=False` 并假设索引已在外部创建，因此“生产库已有并命中 GiST”仍需实际 DDL、`pg_indexes` 和 `EXPLAIN ANALYZE` 证明。另外密度查询返回的是 `ST_SnapToGrid` 后的格点坐标，代码没有额外加半格偏移；把它称为严格“格网中心”并不严谨。

### Q96：推荐能力是在线推理吗？指标能直接使用吗？

**参考回答【代码可核实】：**

> 不是在线推理。`generate_recommendations.py` 从数据库 Session 读取历史，把最后一个签到作为 target，调用仓库中 `RecModel/src/infer_sessions.py` 的 `T10e2SessionRecommender` 离线生成候选；脚本默认导出 CSV，只有传 `--write-db` 才事务性替换对应 Session 和模型的数据库结果。在线 Service 和 Agent Tool 只读取 `recommendation_results`，按 rank 返回 Top-K，并在历史轨迹末点等于 target 时去掉该点，避免把答案当作已知历史展示。

**必须补证：**本轮没有核验模型 checkpoint、训练/测试切分、离线评测原始输出和可复现命令。`app/data/metrics.json` 的代码注释明确称其为 mock 数据，且 `metrics` Router 当前未注册到主应用。因此 HR@5、NDCG@5、MRR@10 及消融数字不能仅凭该 JSON 当作真实实验结论。

### Q97：工具参数治理做到什么程度？

**参考回答【代码可核实】：**

> 公共 `AgentTool.validate()` 会检查必填字段和字符串、整数、数字、对象等顶层类型，并过滤未声明字段；选址工具额外使用 Pydantic，要求 `area_ids` 非空、元素非空白且拒绝未知候选区。LLM 返回未注册工具或非法响应时，路由最多尝试两次，再回退规则路由。

**当前缺口：**公共校验不会递归验证 bbox 子字段，也不执行 JSON Schema 中的范围约束或数组元素约束。本机直接验证发现 `RecommendTool.validate({"top_k": -1})` 和 `SpatialAnalysisTool.validate({"bbox": {}, "grid_size": 0})` 都会通过；前者会产生负数切片语义，后者可能在密度计算时除零。HTTP Query 接口虽然另有 FastAPI 范围约束，但 Agent Tool 调用不经过这些 Query 校验。还需要补 `minimum/maximum`、嵌套必填字段、经纬度范围、bbox 顺序和统一 Pydantic/JSON Schema 校验。
