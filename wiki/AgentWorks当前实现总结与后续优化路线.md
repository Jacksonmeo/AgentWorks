# AgentWorks 当前实现总结与后续优化路线

> 文档基线：2026-09-26 当前工作区代码
> 适用范围：当前后端工作区与同级前端工作区  
> 文档目的：说明当前已经采用的方案、关键实现思路、已知边界，以及从“技术 Demo”继续走向产品化的建议。

## 1. 结论先行

AgentWorks 当前已经不是简单的“输入一句话、调用一次模型、输出一段文本”的聊天 Demo。后端已经形成了一条相对完整的 Agent 运行链路：

```text
记忆读取
  -> 意图识别
  -> 结构化路由
  -> 单 Agent / 多 Agent 协作
  -> RAG 与业务工具
  -> 流式回复
  -> 记忆回写
  -> 监控与评测
```

已经具备的工程能力包括：细粒度意图识别、多 Agent 主辅路由、工具白名单、RAG、三级记忆、动态 Skills、SSE 真流式输出、Markdown 安全渲染、在线监控和 LLM-as-Judge 评测。

当前最明显的短板不在“有没有功能”，而在以下三点：

1. **网页端仍是能力展示台，不是完整业务工作台。** 对话、运行指标、原始用户 ID、知识维护、Skills、评测都直接并列展示，技术信息多，真实客服任务流弱。
2. **系统完成了智能决策，但还没有完成真实业务闭环。** 退款、订单、工单、人工转接目前主要是判断、说明和交接摘要，还没有真正接入业务系统执行。
3. **性能优化已有方向，但缺少端到端分段指标。** 已经减少了多余模型调用并加入流式输出，但还不能在页面上准确回答一次慢请求到底慢在意图、检索、模型首字还是生成阶段。

因此，下一阶段不建议继续堆更多独立功能。更合适的主线是：

> 把 AgentWorks 从“展示所有技术能力的页面”收敛为“客服坐席真正能处理会话的工作台”，再围绕可靠性、数据闭环和可观测性补齐生产能力。

## 2. 当前系统全貌

```text

  │ POST /chat/stream（SSE）
  ▼
FastAPI API
  ├── MemoryManager
  │     ├── Redis：当前会话工作记忆
  │     └── ChromaDB：情景记忆、用户画像
  ├── IntentRecognizer
  │     ├── 显式规则快速路径
  │     ├── LLM 语义识别
  │     ├── Embedding / 本地向量匹配
  │     └── Pattern 关键词兜底
  ├── AgentOrchestrator
  │     ├── GeneralAgent
  │     ├── TechnicalAgent
  │     ├── BillingAgent
  │     ├── EscalationAgent
  │     └── ResponseComposer
  ├── MCPToolManager
  │     ├── 工具校验、超时、缓存、熔断、降级

  ├── Redis
  ├── ChromaDB
  ├── Qdrant
  ├── Prometheus
```

## 3. 已完成方案及实现思路

### 3.1 项目统一为 AgentWorks

项目展示名、容器名、Compose 网络、前端本地存储键、API 标题和主要文档已经统一到 AgentWorks。旧名称不再作为产品名称继续使用。

这次调整不只是页面换字，而是同步处理了运行配置和文档入口，避免出现页面叫 AgentWorks、容器和 API 仍显示旧名称的割裂感。

当前目录名仍保留历史路径，这是本地文件系统层面的名称，不影响运行时产品标识。后续如果要彻底统一，可以在代码稳定、工作区无未提交改动时单独迁移目录，避免路径重命名与业务修改混在一次变更里。

### 3.2 对话主链路

一次请求当前按以下顺序处理：

1. 从 Redis 和 ChromaDB 读取最近消息、历史摘要、相关情景记忆和用户画像。
2. 使用最近对话历史辅助识别意图、意图组、紧急度和实体。
3. 根据意图、关键词、实体和可用 Agent 生成结构化路由决策。
4. 对明确业务意图预取知识库，减少一次“让模型决定是否调用 RAG”的往返。
5. 单领域问题由一个 Agent 处理；复合问题并行运行主 Agent 和辅助 Agent。
6. 多 Agent 结果由 ResponseComposer 去重、处理冲突并形成统一答复。
7. 最终正文通过 SSE 增量返回。
8. 用户消息和完整答复写回工作记忆；满足阈值时异步更新用户画像。
9. Agent 和工具运行数据进入 Monitor，工具明细写入最近请求追踪。

实现上的核心原则是：**能用确定性逻辑完成的判断，不额外调用模型；只有语义判断和自然语言生成交给模型。**

### 3.3 意图识别

意图识别位于 `core/intent_recognizer.py`，当前不是单一 LLM 分类，而是多信号融合：

- 显式规则快速路径：寒暄、明显的人工请求和部分高确定性表达直接返回。
- LLM 分支：处理上下文相关、表达模糊和复合语义。
- Embedding / 本地向量分支：与意图模板做相似度匹配。
- Pattern 分支：以关键词和规则作为稳定兜底。
- 结果缓存：相同消息和上下文可复用识别结果。

识别结果不仅有 `intent`，还包括：

- `intent_group`
- `confidence`
- `source_scores`
- `urgency`
- `entities`

这些结构化字段继续驱动 RAG、Agent 路由、澄清和人工升级，而不是只用于页面展示。

当前选择多路融合的原因，是纯 LLM 识别虽然灵活，但延迟和输出稳定性较弱；纯规则快但覆盖有限。快速路径和缓存优先解决常见问题，复杂问题再进入模型识别。

### 3.4 多 Agent 路由与协作

核心实现位于 `agents/agent_orchestrator.py`。

每类 Agent 都有明确的 `AgentProfile`，包括角色、目标、处理步骤、输入契约、输出契约、升级条件、工具范围、温度和最大输出 token。当前角色为：

| Agent | 主要职责 | 主要工具 |
|---|---|---|
| General | 通用接待、需求澄清、基础咨询 | 知识检索、上下文检查、必填字段建议 |
| Technical | 错误诊断、排障步骤、升级判断 | 知识检索、错误码查询、诊断计划 |
| Billing | 退款、扣款、发票、订阅核验 | 知识检索、账单字段检查、金额比较 |
| Escalation | 人工升级和交接摘要 | 知识检索、交接摘要 |

路由顺序为：

1. CRITICAL 紧急度或明确人工意图优先进入 Escalation。
2. 其他请求按意图、关键词和实体计算领域分数。
3. 最高分作为 `primary_agent`。
4. 分数达到阈值、且与主 Agent 足够接近的领域成为 `supporting_agents`。
5. 同类存在多个实例时，根据成功率、平均延迟和监控降权选择运行状态最好的实例。
6. 专属 Agent 不可用时降级到 General。

多 Agent 场景采用并行执行，避免专业 Agent 串行等待。中间草稿不会直接交叉输出到前端，只有 Composer 形成的最终答复才流式展示，从而保证用户看到的是一条连贯回复。

### 3.5 RAG 与知识库

知识库位于 `mcp/knowledge_base.py`，使用 Qdrant 保存父子块、Dense 向量和 BM25 稀疏向量。当前主要行为是：

- 按标题层级构建不超过约 900 token 的父块，再切成不超过约 240 token、带约 40 token 重叠的子块。
- 显式使用 `BAAI/bge-small-zh-v1.5` 生成中文 Dense 向量，同时使用 Qdrant BM25 多语言 tokenizer。
- Dense 与 BM25 各召回 Top20，由 Qdrant 默认 RRF 配置融合成 12 个候选，不在应用中写死 `k=60`。
- `BAAI/bge-reranker-base` CrossEncoder 对子块重排；证据 Gate 通过后才批量读取最多 3 个父块。
- 导入接口支持文本录入和 `.txt`、`.md`、`.json` 文件。
- 知识检索工具有 5 分钟 TTL 缓存。

RAG 当前采用“直接检索优先、最多改写一次”：

```text
明确问题 -> Dense + BM25 -> 默认 RRF -> CrossEncoder -> 证据 Gate
  ├── 充分：按 parent_id 去重 -> 批量读取 Top3 父块
  └── 不足且未改写：改写一次 -> 重试同一链路
                         ├── 充分：返回父块
                         └── 仍不足：明确无答案
```

只有存在对话上下文且问题指代不清或过短时才预先改写；否则先直接检索。首轮证据不足时也只允许一次改写重试，不做多查询扇出。这样保留了长尾召回能力，同时控制模型调用次数和响应延迟。

明确的业务意图会在 Agent 生成回复前直接预取知识，避免先让模型规划一次工具调用，再进行检索和第二次生成。问候和反馈等请求则跳过 RAG，防止无关知识污染回答。

### 3.6 工具治理和 Skills

`MCPToolManager` 为工具提供统一的可靠性能力：

- JSON Schema 参数校验
- 异步执行与同步 handler 线程池兼容
- 超时控制
- TTL 缓存
- 熔断器
- fallback 降级结果
- 调用成功率、延迟、连续失败统计
- 条件查询改写和检索结果元数据透传

Agent 自身还通过工具白名单限制可调用范围，避免账单 Agent 随意调用技术工具或模型调用未授权能力。

Skills 与知识库承担不同职责：

- 知识库回答“事实是什么”。
- Skills 约束“应该按什么流程处理、哪些话不能承诺”。

`SkillManager` 支持 Markdown、TXT 和 JSON，按 Agent 类型、关键词和启用状态动态注入，并可通过 `/skills/reload` 热加载。单个 Skill 解析失败不会阻塞其他规则生效。

### 3.7 三级记忆

记忆实现位于 `memory/conversation_memory.py`：

| 层级 | 存储 | 当前用途 |
|---|---|---|
| 工作记忆 | Redis | 当前会话最近消息，TTL 24 小时 |
| 情景记忆 | ChromaDB `episodic` | 被压缩的历史对话片段和跨会话语义检索 |
| 用户画像 | ChromaDB `user_profile` | 稳定偏好和关键实体 |

工作记忆达到压缩阈值后，旧消息由模型生成摘要，Redis 只保留摘要和最近消息，同时把历史片段写入情景记忆。

用户画像现在不是每轮更新，而是每 6 条消息，也就是约 3 轮对话触发一次，并使用后台任务执行。这样做的原因是：`asyncio.create_task` 只代表不阻塞当前协程，不代表不会占用同一个模型供应商的并发额度、HTTP 连接和吞吐。降低触发频率可以减少它与下一轮前台回复争抢模型资源。

### 3.8 SSE 真流式输出

流式能力不是把完整答案切成几段假装流式，而是模型 SDK 的正文增量直接进入 SSE：

```text
模型 text_stream
  -> 后端 on_token 回调
  -> SSE delta 事件
  -> 前端累积文本
  -> 每 40ms 批量刷新一次视图
```

`POST /chat/stream` 当前发送五类信息：

| 事件 | 含义 |
|---|---|
| `progress` | 上下文、意图、执行、记忆等可解释业务阶段 |
| `delta` | 模型正文增量，带递增 sequence |
| `result` | 完整结构化响应，作为最终校准结果 |
| `done` | 正常结束标记 |
| `error` | 处理失败信息 |

额外机制包括：

- 15 秒无事件时发送 keep-alive，降低代理空闲断开概率。
- 浏览器通过 `AbortController` 取消请求，新建会话或卸载页面会终止上游流。
- 前端按 sequence 去重，避免重复片段。
- 流中断时保留已经生成的部分正文，并给出明确提示。
- 如果供应商在首字前不支持流式，可安全回退到普通生成；已经输出部分正文后中断则不会静默重试，以免内容重复。
- 达到 `max_tokens` 时最多自动续写一次，不再用“默认 500 字”硬截断回答。

页面展示的是**业务处理进度**，不是模型私有思维链。当前的“正在读取上下文、正在识别意图、正在选择模块”等状态，既能提供反馈，也不会把不可验证的内部推理伪装成事实。

### 3.9 Markdown 渲染

前端使用 `marked` 解析 GFM Markdown，支持标题、列表、表格、引用、行内代码和代码块；之后使用 `DOMPurify` 清洗 HTML，再通过 `v-html` 展示。

相比直接使用 `white-space: pre-wrap`，这一方案解决了 Markdown 标记原样显示的问题；相比直接信任模型输出，DOMPurify 又保留了必要的 XSS 防护。

流式阶段会不断重新解析尚未闭合的 Markdown，因此极端情况下仍可能出现表格或代码块在生成过程中短暂跳动。最终 `result` 事件会用完整正文校准，保证结束后的结构一致。

### 3.10 监控、告警和动态降权

Monitor 默认每 10 秒采集一次 Agent 和工具统计，当前阈值包括：

| 指标 | 告警条件 |
|---|---:|
| Agent 成功率 | 低于 90% |
| 工具成功率 | 低于 95% |
| Agent 平均延迟 | 高于 3000ms |
| 工具平均延迟 | 高于 5000ms |

告警已经按“指标 + 实例”去重，同一个持续异常只更新现有告警，不会每 10 秒新增一条；指标恢复后会把告警标记为已解决。接口只返回最近 10 条**活跃告警**。

Monitor 不只是页面展示。它会把成功率和平均延迟转换成 `monitor_penalty`，再影响 Agent 的 `routing_score`。这使运行状态差的同类 Agent 在后续请求中被降权。

需要注意：当前每类通常只有一个 Agent 实例，因此“动态绕开慢实例”的价值还没有完全发挥出来；此时降权更多是可观测信号，而不是实际故障转移。

### 3.11 端到端评测

`POST /eval/run` 当前覆盖两类评测：

1. 意图识别：Accuracy、Macro-F1 和各类别 Precision / Recall / F1。
2. 对话质量：模型生成回复后，由 LLM-as-Judge 从相关性、准确性、完整性和有用性四个维度评分。

综合评分达到 0.75 视为通过。系统会把本次结果与上次结果或持久化基线比较，某指标相对退化超过 5% 时记录回归项，并根据低分维度生成建议。

此前评测无法正常运行的问题已经围绕模型兼容、返回解析和前端错误反馈做过修复。当前页面能显示通过率、平均分、回归项、耗时、建议和单条用例明细。

它目前仍是同步长请求。评测用例越多，浏览器等待越久，模型调用成本也越高，这会是下一阶段需要优先改造的部分。

### 3.12 模型与成本策略

模型地址和名称通过环境变量注入，Agent、意图识别、记忆、RAG 辅助链路和 Judge 复用同一套兼容接口，业务代码不硬编码供应商。

当前选择 Flash 类型模型，而不是默认升级到更贵的 Pro 类型，核心考虑是客服在线链路更看重首字延迟、吞吐和单位请求成本。现阶段更合理的策略是：

- 先用评测确认 Flash 模型在哪些意图和任务上已经够用。
- 通过规则、检索和工具补足事实性，而不是全部依赖更大模型。
- 关闭隐藏思考，减少不可见的耗时和 token。
- 按 Agent 设置不同温度和 token 上限；技术、账单允许更完整，通用问题更简洁。
- 不再按 500 字硬裁剪，命中 token 上限时最多自动续写一次。
- 后续若确有质量差距，只把低置信度、复杂推理或高风险请求升级到更强模型，而不是全量切换。

因此，是否使用更贵模型应由“分场景评测增益 ÷ 成本与延迟增加”决定，而不是仅凭单次主观体验决定。

## 4. 前端现状与“Demo 感”的来源

### 4.1 已完成的前端改进

当前前端已经完成以下基础改造：

- 使用 AgentWorks 品牌，去除旧项目名。
- 统一较克制的绿色、灰白视觉，不再使用大面积渐变和常见 AI 紫色风格。
- 整体字号提升，不依赖 `<small>` 标签表达辅助信息。
- 删除与核心体验关系较弱的“检查连通”和 Java 服务面板。
- 保留客户对话、知识库和评测三个核心入口。
- 支持真实 SSE 增量正文、处理进度、取消请求和中断保留。
- 支持安全 Markdown、表格、代码块等内容展示。
- 支持知识检索、录入、文件上传、Skills 查看和热加载。
- 支持评测摘要、指标条、建议和明细。
- 响应式适配桌面、平板和移动宽度。

### 4.2 为什么使用时仍然像 Demo

问题不是简单的“颜色还不够漂亮”，而是产品信息架构仍然以开发验证为中心。

#### 角色不够明确

页面同时面向四种角色：

- 与机器人对话的终端用户
- 处理客户问题的客服坐席
- 维护知识和 Skills 的运营人员
- 查看监控和评测的研发人员

这些角色需要的信息不同，却被放进同一个顶层页面。用户会感觉每个功能都有，但不知道这个产品最核心的使用者是谁。

#### 对话区缺少真实工作上下文

现在右侧主要展示用户 ID、会话 ID、路由、意图、耗时和告警。这些对调试有用，但对客服处理问题帮助有限。真实坐席更需要：

- 客户基本资料和标签
- 当前订单、退款、订阅或工单状态
- 历史会话列表
- 待办事项和 SLA
- 可执行动作，例如创建工单、申请退款、转交部门
- 知识引用和回答依据

#### 页面状态只是浏览器临时状态

当前消息数组保存在 Vue 内存中，刷新页面后 UI 对话记录消失；`conversationId` 虽然保存在 localStorage，页面却没有会话列表和从后端恢复完整消息的接口。用户 ID 也由输入框直接编辑，更像接口调试参数。

#### 管理能力只有“操作”，缺少“治理”

知识库目前可以搜、加、上传，但缺少文档列表、版本、状态、来源、权限、删除、编辑和命中统计。评测可以运行，但缺少评测集管理、历史趋势、任务队列、结果对比和失败用例复跑。

#### 技术字段直接暴露

`technical_login`、`billing`、`routing_confidence`、请求 ID 和工具输入对研发排障有价值，但直接放在主体验中会强化 Demo 感。更适合放在可折叠的“诊断模式”或独立管理台中。

#### 前端代码结构仍适合原型，不适合持续扩展

当前主要页面、状态和请求逻辑集中在一个 `App.vue` 中，没有路由、全局状态层和领域组件拆分。对现阶段功能量仍能工作，但继续添加会话列表、用户详情、知识管理和评测历史后，修改风险会快速上升。

## 5. 当前性能方案与仍然慢的原因

### 5.1 已经完成的性能优化

- 明确意图使用快速规则，避免所有请求都调用意图模型。
- 意图识别结果增加缓存。
- 关闭模型隐藏思考，减少无意义 token 和等待。
- 明确业务意图直接预取 RAG，省掉一轮工具规划模型调用。
- RAG 先直接检索，只有无结果才执行查询改写和重排。
- 检索结果去重，减少重复上下文。
- 多 Agent 并行执行，不串行等待。
- 用户画像降低为约每 3 轮异步更新一次。
- ChromaDB 同步调用放入线程池，避免阻塞事件循环。
- 真流式输出降低体感等待，前端以 40ms 批量渲染降低频繁更新开销。
- Agent 和 Composer 设置不同的输出 token 上限，命中上限时只续写一次。

### 5.2 为什么仍会慢

首字出现之前仍然需要完成部分前置步骤：

```text
读取记忆 -> 意图识别 -> 路由 -> RAG -> 模型首字
```

其中任何一个外部服务抖动都会增加 TTFT。复杂问题还可能走：

```text
多个 Agent 并行完整生成 -> Composer 再生成最终回答 -> 首字输出
```

虽然 Agent 是并行的，但 Composer 必须等草稿全部完成，所以多 Agent 场景的首字天然更慢。

编写本文时的本地运行快照中，General Agent 平均约 3.6 秒，Technical Agent 平均约 20 秒，但样本分别只有 4 次和 2 次，不能当作稳定基准。它至少说明了两件事：

- 当前 3000ms 的统一告警阈值会对长回答频繁告警。
- 只有总耗时无法判断慢在 RAG、模型 TTFT 还是正文生成。

因此下一步最有价值的性能工作不是继续凭感觉删除模块，而是先补齐分段耗时。

### 5.3 建议新增的性能指标

每个请求至少记录：

- `memory_read_ms`
- `intent_ms` 与识别路径（fast/pattern/embedding/llm/cache）
- `rag_ms`、命中数、是否改写、是否重排、是否缓存命中
- `routing_ms`
- `model_ttft_ms`
- `model_generation_ms`
- `composer_wait_ms`
- `memory_write_ms`
- `total_ms`
- 输入/输出 token 和估算成本

前端默认只展示“正在处理”，诊断模式再展示分段瀑布。这样既不影响普通用户体验，又能准确定位性能问题。

## 6. 已知技术边界

### 6.1 前端

- 单个 `App.vue` 承担过多职责，后续扩展成本高。
- 没有正式路由和页面级加载策略。
- 没有登录、权限和租户概念。
- 没有会话历史列表和刷新后的消息恢复。
- 缺少复制、重新生成、停止生成、赞踩反馈和重试等成熟对话交互。
- 流式 Markdown 对未闭合表格、列表和代码块可能暂时抖动。
- 没有代码高亮、引用卡片和知识来源跳转。

### 6.2 Agent 与业务执行

- 当前工具以演示性检查、知识检索和摘要为主，没有真实订单、退款、支付、工单 API。
- Escalation 只生成交接内容，没有真正创建人工工单。
- 多 Agent 是否触发仍以启发式分数为主，缺少基于真实数据的路由校准。
- 每类默认只有一个实例，性能路由和自动绕行的实际收益有限。

### 6.3 RAG

- 已按 Markdown 标题、段落和句子边界实现通用父子切块，但表格、代码块和 FAQ 尚无专用解析器。
- Dense、BM25、默认 RRF 和 CrossEncoder 已接入，但 Gate 阈值仍需用固定业务问题校准。
- 没有租户、产品、语言、版本、生效时间等 metadata 过滤。
- 已有内容哈希、文档版本和 active 标记，但还没有完整的删除 API、来源清单、权限管理和 alias 换版流程。
- 检索质量缺少独立 Recall@K、MRR、NDCG 评测集。
- fallback 和无答案已通过 `sufficient=false` 区分，但仍需在完整前端交互中验证呈现方式。

### 6.4 记忆

- 工作记忆有 TTL，但前端没有完整会话恢复体验。
- 画像是模型提炼结果，缺少字段 schema、置信度、来源和用户纠错机制。
- 压缩在达到阈值时仍属于消息写入链路，可能导致某一轮尾部延迟变高。
- 后台任务没有独立队列，进程退出时未完成任务可能丢失。

### 6.5 评测

- 默认用例数量较少，容易对真实业务覆盖过于乐观。
- 生成与 Judge 使用同一模型体系，存在自评偏差。
- 评测是同步请求，没有任务 ID、进度、取消和历史查询。
- 基线只有单份文件，缺少模型版本、Prompt 版本、知识库版本关联。
- 当前前端指标名称需与后端四项评分继续保持一致，避免出现 UI 预留项与实际字段不一致。

### 6.6 监控与安全

- 统计和工具追踪主要在进程内，重启后历史有限。
- Prometheus 已接入，但缺少完整 Grafana 看板和告警规则管理。
- 静态统一阈值没有区分短回答、技术排障、多 Agent 合并等请求类型。
- CORS 当前允许全部来源。
- API 没有认证、RBAC、限流、审计日志和租户隔离。
- 文件上传主要校验大小和扩展名，生产环境还需要 MIME、内容安全和恶意文件检查。
- SSE 没有事件恢复 ID，断线后只能重新请求，不能从上一个序号继续。

## 7. 推荐优化路线

### 7.1 P0：先从 Demo 变成可用工作台

目标：让第一次打开页面的人能立刻理解“这是客服坐席工作台”，而不是 API 能力集合。

#### 方案 A：重做信息架构

建议把产品拆成两个清晰区域：

```text
坐席工作台
  ├── 会话队列
  ├── 当前对话
  ├── 客户与业务上下文
  └── 建议动作 / 转人工 / 工单

管理中心
  ├── 知识库
  ├── Skills
  ├── 评测
  └── 监控与诊断
```

普通坐席默认看不到原始路由分数和工具参数；研发或管理员打开诊断模式后再查看。

验收标准：

- 首页只围绕处理客户会话展开。
- 用户 ID 和会话 ID 不再作为主表单字段暴露。
- 知识、评测、监控进入独立管理入口。
- 一次会话中能直接看到客户资料、业务对象和下一步动作。

#### 方案 B：补会话生命周期

新增会话列表、会话详情查询、消息恢复和会话状态。至少支持：新会话、进行中、待人工、已结束。

验收标准：刷新页面后可以恢复历史消息；不同会话可切换；会话状态可追踪。

#### 方案 C：完善核心对话交互

加入停止生成、重新生成、复制、赞踩、失败重试、引用来源和明确的空/错/加载状态。处理进度默认保持简洁，详细 trace 收进抽屉。

验收标准：网络中断、模型报错和用户主动取消时都能恢复到可继续操作的状态。

#### 方案 D：拆分前端但不过度设计

建议最小拆为：

```text
views/
  ChatWorkspace.vue
  KnowledgeCenter.vue
  EvaluationCenter.vue
components/
  ConversationList.vue
  MessageList.vue
  MessageItem.vue
  ChatComposer.vue
  CustomerContext.vue
  ProcessTrace.vue
composables/
  useChatStream.js
  useWorkspaceData.js
```

现阶段不必为了“架构完整”引入大型状态框架；先用 Vue Router 和 composables 把职责分开，出现真正跨页面共享状态后再决定是否使用 Pinia。

### 7.2 P0：先量化性能，再继续优化

给请求全链路加入分段计时、模型 TTFT、token 和成本指标，并在 Prometheus 中按 Agent、意图、是否 RAG、是否多 Agent 分标签观察 P50/P95/P99。

验收标准建议：

| 场景 | TTFT 目标 | 完整响应目标 |
|---|---:|---:|
| 寒暄/明确简单问题 | < 1.5s | < 4s |
| 单 Agent + RAG | < 3s | < 10s |
| 多 Agent 复杂问题 | < 6s | < 20s |

这些目标需要以真实部署网络和模型供应商重新压测，不能直接把本机小样本当成生产 SLA。

有了分段数据后再做针对性改造：

- 意图慢：增加高频规则覆盖，或换成本地小模型分类。
- RAG 慢：优化索引、过滤和缓存，减少无意义改写。
- 模型 TTFT 慢：检查供应商并发、连接复用、区域网络和上下文长度。
- 多 Agent 慢：限制只在真正复合意图时触发，或先流式输出主 Agent 的安全前置回复。
- 生成慢：收紧回答结构和 token 预算，而不是硬截断正文。

### 7.3 P1：补真实业务闭环

优先选择一条完整场景做深，而不是同时接很多浅工具。推荐从“退款/账单”或“技术工单”二选一。

以退款为例：

```text
识别退款意图
  -> 提取订单号
  -> 查询订单和支付状态
  -> 校验退款资格
  -> 展示依据与可执行动作
  -> 用户确认
  -> 创建退款申请或人工工单
  -> 回写状态并持续跟踪
```

必须区分“查询类工具”和“有副作用工具”。有副作用操作需要明确确认、幂等键、权限校验、审计日志和失败补偿，不能仅由模型一句话触发。

验收标准：至少一个业务场景能从咨询走到真实状态变更，并可审计、可重试、可人工接管。

### 7.4 P1：补齐 RAG 数据与线上校准

父子切块、显式中文 Embedding、Dense + BM25、默认 RRF、CrossEncoder、证据 Gate 与条件改写已经完成。后续只做工程收尾：

1. 为知识增加租户、产品、版本、来源、更新时间和状态 metadata。
2. 返回更完整的来源链接，让回答中的依据可点击查看。
3. 准备一组小而固定的业务问题，校准 Gate 阈值并观察无答案误答。
4. 将 ChromaDB 中的长期记忆迁移到 Qdrant，完成后删除过渡期服务和依赖。

验收标准：每条基于知识的答案都有来源；知识无命中时明确说明，不把 fallback 文案误当作事实。

### 7.5 P1：把评测改为任务系统

建议将 `/eval/run` 改成异步任务：

```text
POST /eval/jobs -> 返回 job_id
GET /eval/jobs/{id} -> 状态与进度
GET /eval/jobs/{id}/results -> 完整结果
POST /eval/jobs/{id}/cancel -> 取消
```

评测任务进入独立队列，不与在线对话争抢同一并发池。评测结果关联模型、Prompt、Skills、知识库版本和代码提交。

验收标准：关闭或刷新网页不影响任务；能查看历史趋势；失败用例可单独重跑；在线对话延迟不因评测明显升高。

### 7.6 P2：生产可靠性与安全

- 接入登录、RBAC 和租户隔离。
- 收紧 CORS，增加限流、输入长度限制和审计日志。
- 将画像更新、记忆压缩、评测等后台任务迁入可靠队列。
- 为外部工具增加幂等、重试退避、死信和补偿策略。
- 使用 OpenTelemetry 串联前端请求、API、Agent、模型和工具 trace。
- 建立 Grafana 仪表盘和按请求类型区分的告警规则。
- 增加单元测试、API 契约测试、SSE 集成测试、浏览器 E2E 和并发压测。

验收标准：关键操作可追踪、关键数据可隔离、服务重启不丢后台任务，发布前有自动回归门禁。

## 8. 建议的产品形态

如果目标是继续做成作品集或面试项目，最值得投入的不是增加 Agent 数量，而是完成一条可演示、可解释、可量化的业务故事：

> 客服进入会话队列，看到客户与订单上下文；Agent 实时给出有知识来源的建议；客服确认后执行一项真实业务动作；系统记录完整 trace；评测和监控能证明改动没有让质量退化。

如果目标是实际落地，建议明确两套界面：

- **坐席端**：强调会话、客户上下文、建议动作和人工控制。
- **管理端**：强调知识、规则、评测、监控、权限和审计。

当前网页可以继续作为管理端原型，但不应再让它同时承担终端用户聊天页、坐席台和研发控制台三种定位。

## 9. 推荐执行顺序

| 顺序 | 工作项 | 价值 | 复杂度 |
|---:|---|---|---|
| 1 | 明确坐席端/管理端信息架构 | 直接降低 Demo 感 | 中 |
| 2 | 分段耗时、TTFT、token 和成本观测 | 找到真正性能瓶颈 | 中 |
| 3 | 会话列表、历史恢复、状态流转 | 形成完整使用闭环 | 中 |
| 4 | 停止/重试/复制/反馈/知识引用 | 提升日常可用性 | 低到中 |
| 5 | 拆分 `App.vue` 和 API composables | 为后续迭代降风险 | 中 |
| 6 | 选一个真实业务场景接入 | 从智能建议走向业务执行 | 高 |
| 7 | 异步评测任务与历史趋势 | 建立稳定迭代闭环 | 中到高 |
| 8 | RAG metadata、来源引用和 Gate 校准 | 提升知识可靠性 | 中 |
| 9 | 认证、RBAC、审计、限流、租户隔离 | 满足生产要求 | 高 |

建议先完成 1—4，再决定视觉细节。没有信息架构和真实工作流支撑时，只调整配色、阴影、圆角，仍然会像一个更漂亮的 Demo。

## 12. 一句话总结

AgentWorks 当前的后端骨架已经具备“可路由、可检索、可记忆、可流式、可监控、可评测”的 Agent Runtime 形态；下一阶段真正拉开差距的不是继续增加技术名词，而是把前端收敛成明确角色下的工作流，并接通至少一条真实、可审计的业务闭环。
